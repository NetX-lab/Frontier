# DP-init rendezvous port divergence: CPU reproduction and bounded findings

Frozen native source under test:
`/data/ycfeng/Frontier/.real-engine/vLLM-BS/.worktrees/glm-h5-clean-2cf0a69`
(`pyproject.toml` declares `torch == 2.13.0`; the tree's git objects are
incomplete in this checkout, so identity is recorded by file SHA-256 in every
`manifest.json` instead).

Formal failure being explained: `exp-1102-164536-160317` (`dsv4-h200-p2-64-formal-20261102-01`),
decode head `gpu-h200-0760` logs `parallel.py:655 Address already in use.
Retrying with a new port.` and never becomes ready; peers keep retrying
`10.204.22.14:40273`; everything is stopped ~30 minutes later.

This work did **not** touch the frozen source, the package, the worktree, or
the platform. Everything below is under
`/data/ycfeng/tmp/ds4_runs/p64-dp-port-repro-1102f/scratch`.

## 3. Is rank0's retry communicated to peers? (mechanism + log reading)

**No, and it cannot be.**

* The retry only re-enters `_pick_stateless_dp_port()` (`parallel.py:641`); in
  the non-elastic mode that pops rank0's *own* list (`:593-594`, `:578-579`).
  There is no store write anywhere in this branch.
* Peers already built `init_method = tcp://<head>:40273` (`utils.py:622`) and are
  inside torch's `rendezvous` client, which retries that same URI
  (`utils.py:645-647`), with the 1800 s default store timeout. They are
  TCPStore *clients*: they never bind, so even if the port became free they
  would keep failing to connect and would never discover rank0's new store.
* Consequently the retry cannot converge: rank0's new store waits for
  `world_size - 1` clients that are all dialing the old port. The only exits
  are rank0's store timeout and each peer's rendezvous timeout. The CPU repro
  shows exactly that shape: rank0 `DistStoreError "Timed out ... 1/4 clients
  joined"` on port B, peers `DistNetworkError "Connection reset by peer"` on
  port A.

Real-log observations (paths under
`/data/ycfeng/tmp/glm53_dsv4/h200/downloads/formal_p2_64_20261102_01/dsv4-h200-p2-64-formal-20261102-01/artifacts/nodes`):

* decode head `gpu-h200-0760…/server.log:59`, 12:22:14:
  `(EngineCore_DP0 pid=1495) WARNING … [parallel.py:655] Address already in use. Retrying with a new port.`
  Nothing is logged about which port was retried, and nothing is logged again
  until the 12:50:44 shutdown (`:60-65`).
* decode peers `gpu-h200-0819…/server.log:14` (12:22:14.227), `:51` (try=0,
  `timeout=1800000ms`), `:458` (try=6, `Ping failed, invalid value returned
  from server. Expected: 1327, Got: 255`), retries continue to 12:50:51
  (shutdown `:3009`). `0828` and `0882` show the same pattern against
  `10.204.22.14:40273`.
* All three decode peers name the **same** remote port 40273 across three
  different hosts; `grep -c "Waiting for READY message from DP Coordinator"`
  is 0 for `0760/0819/0828/0882` (they never got past DP group init), while the
  prefill group head `gpu-h200-0043…/server.log:414` reached
  `All engine subscriptions received by DP coordinator` and prefill DP3
  (`0375:356`) reached the READY wait. The failure is specific to one DP group's
  rendezvous port, not to the deployment as a whole.
* `serve.py:231` on `0819` prints the *DP RPC* head address
  `tcp://10.204.22.14:24571`; that is a different port from the failing 40273.

What the logs **prove**: one rank of one DP group hit EADDRINUSE on its first
rendezvous bind, retried on another port, and its peers never stopped dialing
the old one; the peers' client never validated a TCPStore on 40273 (one reply
did not even carry the TCPStore validation value), so the listener on 40273 was
not the group's own store. The prefill group completed the same code path
successfully.

What the logs **do not prove**:
* who owned 40273 on `gpu-h200-0760` at 12:22:14 (no socket/owner snapshot, no
  pid, no start-time evidence was downloaded);
* the exact port rank0 retried on (never logged), hence the exact four-port
  sequence cannot be reconstructed from logs; only that it was not 40273;
* whether the owner was a leftover from an earlier attempt/run, a co-located
  vLLM process, or an unrelated process. The reproduction proves the *failure
  mechanism*, not the identity of the original port owner.

Inference (marked as inference): because `get_open_ports_list()` is
deterministic only when `VLLM_PORT` is set (`network_utils.py:190-213`, the
else-branch uses a random ephemeral bind), three independent peers agreeing on
40273 implies the launcher exported one `VLLM_PORT` base to all nodes. That
also means the head's port list was the same list, so its first attempt was
very likely 40273 as well — consistent with, but not proof of, an external
owner on the head node.

## 4. Reservation lifetime of `get_open_ports_list`

`_get_open_port()` (`network_utils.py:216-247`) finds a free port by binding and
then **closing** the probe socket inside a `with` block (`:225-228`; the
`bind(("",0))` fallback is `:239-247`). `get_open_ports_list()` just collects
five such values. There is no reservation, no fd kept, and no lock shared with
other processes. The list is a snapshot taken at `ParallelConfig.__post_init__`
(`parallel.py:879-884`) and consumed later at DP group init
(`core.py:2028`); in the formal job that window is ~64-75 s
(config logs 12:20:59-12:21:10, EADDRINUSE 12:22:14).

`runs/canonical_v3/probe_reservation/reservation_probe.json` (native function,
same interpreter): all 5 listed ports rebind successfully, in the same process
and from a separate child process. So the "prepared port list" holds nothing;
any process on the head node can take a listed port between config and use.

Also relevant: with `VLLM_PORT` unset, two independent processes derive
completely different 5-port lists (`probe_list_determinism`: with the env var
the two lists are identical, without it they share no port). Agreement of the
DP rendezvous port therefore depends on the launcher's environment, not on any
coordination in the code.

## 5. Smallest concrete repair options (not implemented here)

All options are evaluated only for the port-selection/rendezvous step; none is
shipped, and all need the lead's/user's approval.

**A. Fail fast instead of retrying blindly (smallest).**
In `stateless_init_dp_group()`, when `_coord_store_port == 0`, do not `continue`
on EADDRINUSE: raise a clear error naming host/port and the fact that peers
cannot learn a new port. Cost: one branch; no healthy-path change.
Measurement implication: the 1800 s hang becomes an immediate failure; the
error text becomes an assertion target; no timing change on success.

**B. Reuse the coordinated publish path that already exists in this source.**
`_pick_stateless_dp_port()`'s coord-store branch (`parallel.py:596-609`) already
implements "rank0 binds `(ip, 0)`, publishes, peers read" and hands the
pre-bound socket to `create_tcp_store` (`utils.py:634-643`), which removes the
re-bind TOCTOU. Today it is wired only for elastic EP: the API server creates
the store (`core_client.py:1693-1700`) and ships its port to workers in
`ReconfigureDistributedRequest` (`:1714-1716`). Extending it to the normal
multi-node DP path needs one store created before engine start and its port
propagated to EngineCore (env var or request field).
CPU validation of that exact branch: `runs/canonical_v3/coord_store_path`
(4/4 ranks `ok` on one published port 40829, rank0 `listen_socket=True`, the
fixed port 47412 deliberately occupied and untouched, no retry warning,
2.8 s). Implications: adds one TCPStore dependency at startup and a new
config/env surface; no effect on post-init timing; must be measured against
the current startup path.

**C. Keep the current list but bind once and keep the fd.**
Have rank0 bind the chosen port at config time and pass the listening socket
through to group init (the `listen_socket` argument already supports this).
No new external store, but it needs fd inheritance/handoff across the
API-server → EngineCore `mp.Process` boundary and explicit lifetime ownership.
More invasive than A/B; only worth it if an extra store is unacceptable.

Recommendation for the lead: A as the immediate blocking fix, B as the durable
one, with the coord-store CPU evidence as the validation baseline for B.
Not investigated here (out of scope): why the head node's port was occupied,
and the exact native startup timing impact of B.

## 6. Proof boundary and limitations

* The frozen package cannot be imported in this environment: with the CPU
  interpreter used here, `vllm.config.parallel` fails at import
  (`ImportError: Support for Transformers v4 is deprecated …`, recorded in
  `runs/canonical_v3/import_probe/import_probe.json`); with `/usr/bin/python3`
  it fails earlier (`torch.library.infer_schema`). `pyproject.toml` declares
  `torch == 2.13.0`, while this host has CPU torch 2.8.0 / 2.1.0.
  Therefore the harness **executes the verbatim source text** of the native
  functions (`native_extract.py`), sliced by AST with recorded spans and
  SHA-256 of each file (`manifest.json`). It does not re-implement the
  algorithm: the same statements, imports, retry loop, `pop()` ordering and
  gloo init run; only `ParallelConfig` the object, the `vllm.envs` accessors
  and `vllm.config.get_current_vllm_config_or_none` are small shims, because
  those modules import the GPU/platform stack. The shim config reads its
  defaults (including `_coord_store_port = 0`) out of the frozen source.
* Network is loopback only (`127.0.0.1`), one process per rank on one host, and
  the DP timeout is shortened to 8-10 s (`REPRO_DP_TIMEOUT_S`) instead of the
  native 1800 s. The timeout value is not part of the bug; the failure shape is
  identical (rank0 waits for clients, peers retry a stale port).
* The "occupied port" is a scratch listener that accepts and immediately
  closes, chosen only to imitate `Connection likely closed/reset` behaviour seen
  in the real peer logs. It is **not** evidence about the original owner.
* No GPU, no vLLM engine, no CUDA, no model; startup phases before/after DP
  group init are not exercised. This is a mechanism reproduction, not a full
  GPU startup reproduction.
* `DistNetworkError` with `"EADDRINUSE"` in the message requires torch >= 2.6
  (torch 2.1 raises `RuntimeError` with `errno: 98` and no `EADDRINUSE`
  substring, so the native retry branch would not even fire there); torch 2.8
  reproduces the native branch. The native runtime's own torch produced the
  same branch in the formal job, so this is a harness-version constraint, not a
  behavioural difference.
