## Recommended first decision

Add one optional observer step identity to `SchedulerOutput`, assigned at scheduling time when observation is enabled. The identity combines the run ID, engine process instance, and engine-local step sequence. Existing request/token/connector fields remain authoritative; do not duplicate them in a separate RPC payload. Worker-local forward identities reference this step identity. Sampling reads the native retained execute state. Clean mode leaves the optional field unset and emits no detailed trace.

The data format change is observation-only. It does not change queue tuples/order, scheduling decisions, sampling, Future completion, output objects, streams, or collective completion. The recorder has one versioned raw record format; process manifests carry stable run/source/rank/group metadata to avoid duplicating configuration at every hook.

### Raw contract

- Manifest: schema version, run ID, pinned source SHA, instrumentation SHA, model/runtime config identity, serving Replica/role, engine request owner, node/process instance, global/local rank and TP/DP/PP/EP membership, expected rank set, mode, configured buffer capacity and diagnostic sampling rule.
- Record: process-local sequence, event kind, local clock domain/unit, step/forward/request/transfer identity as applicable, parent identity, native token state, actual/padded shape, phase, dispatch decision, and observed backend/piece identity where available.
- Host durations require the same process clock domain. CUDA event durations retain their own device/stream domain and are not absolute host timestamps. No cross-host subtraction, zero fill, clamp, or inferred timestamp mapping.
- DP collective identity uses the observed group incarnation and actual invocation sequence plus each rank's parent forward. It is not a positional join of request forwards.
- Transfer identity includes local/remote engine/request, KV group, attempt and handle incarnation. `start_load_kv`, preparation, READ submission, observed handle DONE, worker-ready and scheduler-ready remain separate. DONE-observation duration includes polling delay, not exact wire time; failed receives are not successful KV readiness.
- Graph dispatch is distinct from actual capture/replay pieces. Unknown or missing graph evidence remains unverified, not an eager default.
- Process footer: final sequence/count, drop count, pending scopes/events, flush error, and normal/abnormal completion. The driver checks the expected rank manifest and platform/container terminal evidence. Missing footer, missing rank or SIGKILL is incomplete, never PASS.

## Approved causal READ object/lifetime association

### Evidence and purpose

Read-only planner `4fc2685b-b229-4bb` and primary verified the native object path. V1 mixin `_get_kv_connector_output` holds the current SchedulerOutput, binds its actual connector metadata without copying, then calls native `start_load_kv`. That metadata creates a distinct ReqMeta for each receive dispatch. Background handshake callback retains the exact `(request_id, meta)` tuple; the main worker later consumes the original object. `_read_blocks_for_req` creates ReadSpec while holding that ReqMeta and passes the same ReadSpec to `_read_blocks`. Native prepare returns an integer handle before submission and append; numeric reuse is not lifetime identity.

Existing records cannot recover that path retrospectively. The current recorder has no object index or retained lifetime state. Matching request IDs, current step, adjacent records or handle numbers would misassociate delayed handshakes and retries. Existing group membership and process sequence do not repair this.

### Recommended extension

Reuse the current recorder and native objects: original SchedulerOutput parent -> actual ReqMeta object -> actual ReadSpec object -> process-local handle lifetime created only after native prepare returns. A bounded observer-only object index uses weak references and validates referent identity, not dataclass equality, block hashes or bare id values. Native RPC, metadata, methods, callbacks, queue tuples/order, outputs and peer messages stay unchanged. Main-thread hooks only; no active/last parent, background-thread recorder, extra calls/waits/device reads or flush changes.

Each successfully retained source identity record may create a small index entry; index growth must be bounded using the existing explicit recording capacity/admission, with no large block arrays or strong reference to SchedulerOutput. Encoding capacity is not a promise that every Python allocation is byte-bounded. Overflow, expired reference, collision, missing parent and unresolved lifetime remain incomplete. Exact capacity accounting and tests must be reviewed in the first implementation card before acceptance.

A handle lifetime begins at actual successful prepare return and ends only after observed native release returns. Same numeric handle reused after an observed release gets a distinct lifetime. A live-handle collision is unknown/incomplete, not silently overwritten. DONE before telemetry/release failure does not close lifetime. One handle may cover multiple KV groups; do not create fictitious per-group native transfers.

This extends retained observer identity/lifetime and raw pending semantics. Those were excluded from the prior bounded host-only cards; approval is required before implementation. It does not classify expected startup/profile dummy records differently: the existing footer missing-parent rule remains unchanged.

### Limits that remain unknown

The native failure queue retains request ID but discards the originating ReqMeta/attempt. A current metadata lookup cannot prove the asynchronous failure's original attempt. Worker receive-report and cross-rank aggregation also reduce results to request IDs; scheduler promotion requires additional causal evidence. Producer notifications do not carry the local handle lifetime. Do not invent identity for these paths. The proposed mapping can link directly observed local READ creation/submission/DONE/release, not all failures, remote attempts or scheduler readiness. Native serialization/retention, actual transfer paths and clean/light perturbation still need runtime validation. Complete schema/G0-C remains open.
