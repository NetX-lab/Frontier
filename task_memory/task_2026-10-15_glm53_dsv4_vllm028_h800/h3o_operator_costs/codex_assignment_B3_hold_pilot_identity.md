### 2. Runner phases (`dsa_vllm_runner.py`)

1. Every `execute_model` wrapper uses `functools.wraps`, so `inspect.signature(original)` follows `__wrapped__` to the native method. The case recorder binds the call with `inspect.signature(original).bind(scheduler_output, *args, **kwargs)` plus `apply_defaults()` and reads `dummy_run` (named constant for the parameter name). It reads this before the "no requests" early return of `begin_step`, because dummy outputs carry no requests (`begin_step` gains a `dummy_run` argument).
2. Matching in `begin_step`:
   - a `dummy` case matches iff `dummy_run`; no other case matches a dummy run;
   - `first_tail` matches when `len(requests) == batch_size`, exactly one request has `num_scheduled_tokens == 1` and `num_computed_tokens + 1 == prompt_len`, and every other request has `num_computed_tokens >= prompt_len`;
   - `prefill` and `decode` keep their rules.
3. `_WorkerState.matched_dp_peer`: on a match, before the skip / limit check (warmup steps also run with the peer), set it to the case's peer; the wrapper clears it in a `try/finally` around both the recorded and the unrecorded call.
4. `begin_case` gains `dp_peer` (a plain mapping or `None`, picklable through `collective_rpc`); `_case_window` returns `(warmup, measured)` for `first_tail` and `dummy`. A dummy step record has `requests: []`.
5. Drivers in `run_case`:
   - `first_tail`: add the `batch_size - 1` decode requests (`max_tokens` = the case's `max_tokens`) and step until every one of them has returned at least one output token (from the `RequestOutput`s of `llm_engine.step()`), bounded by `max_steps`; only then `begin_case` (build steps are neither matched nor traced); then per repeat add one tail request (prompt `prompt_len`, `max_tokens` 1) and step until it finishes; then `abort_request` the decode requests and drain. Requests and their ids follow the existing label scheme.
   - `dummy`: `begin_case`, then `warmup + measured` calls of `llm.collective_rpc(run_dummy_step)`, where the worker function `run_dummy_step(worker)` calls `worker.execute_dummy_batch()` then `close_step_range()` of section 4.
   - Then `finish_case` and the existing `recorded == limit` check and trace handling.
6. The eager runners' behaviour (eager-chunked and native-defaults plans never contain the new phases) stays unchanged.

### 6. Reducer (`dsv4_replay_gaps.py`)

1. Allow activity `hold`. A hold is a dependency end in every rule (it counts in R1, the same-stream predecessor and the layer entry end) and never a gap sample (not `eager_preparation`, not a NONE unowned diagnostic).
2. Any activity of the step that starts before its hold ends is excluded with reason `overlaps_hold`.
3. Invariants: the engine record must carry `step_hold_us` and `hold_cycles_per_us`; a step of an engine with `step_hold_us > 0` has exactly one hold, otherwise none.
4. Per step slack = hold end − the largest `launch_end_us` of the step's attention-owned activities. Diagnostics per (step `cg_mode`, `case_id`): step count; realized hold duration min / median / max; slack min / median; counts of attention-owned and of unowned activities whose launch ended after the hold ended. (Negative slack means a launch was issued after the device was released: a host synchronization or a full launch queue.)
5. Everything else (values, classes, CSV rule, existing diagnostics) is unchanged; on hold-free data the diagnostics equal the B2 output apart from the hold-related additions.
