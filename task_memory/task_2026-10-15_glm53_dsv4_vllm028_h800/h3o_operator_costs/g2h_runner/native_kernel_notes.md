## Native layout and reduced experts

The grid selects 43 native layers, 8 routed experts and native top-k 6. It keeps `num_hash_layers=3`, compressor ratios, KV head/head-dimension parameters and dtype. The existing engine builder retains replay TP8-local attention dimensions at physical TP1; only `n_routed_experts` is added to its HF overrides. Direct startup selects eager policy and clears graph capture settings and the unused replay hold; measured holds still come from the direct grid.

Evidence chain for per-block layout independence from routed experts:

- `nvidia/model.py:554-559,573,581-593,694` uses expert count for FFN routing, gate width, hash IDs and expert allocation. Hash dummy IDs use `torch.randint(0,n_routed_experts,(vocab_size,top_k))`; the reduced range is valid. Divisibility at 678-684 permits 8 at physical TP1. These fields are not read by the attention constructors/spec methods.
- `attention.py:193-218` derives attention dimensions and compression from attention/cache config and layer index. `attention.py:716-741,762-779` constructs compressed attention/indexer specs from block size, head size, dtype, compression and alignment. `compressor.py:182-205` derives compressor state block sizes 4/8 and specs from compression, state dimension, window and dtype. Its backend tensor shape/stride rule is at 82-104.
- `v1/core/kv_cache_utils.py:1545` (`group_and_unify_kv_cache_specs`) and 1741 (`get_kv_cache_groups`) operate on those specs. Frontier's existing B4 port is `frontier/attention/deepseek_v4.py:63`; CPU planning uses it, rather than adding another layout implementation. For 43 layers it yields five groups with member counts `[62,22,21,42,20]` (167 logical members); every actual member is compared at runtime.
- `v1/worker/utils.py:139-199` constructs the zeroer's segments from attention groups, actual KV tensor pointers (deduplicated), backend block dimensions, tensor strides/outer dimensions and virtual block splitting. Metadata/chunk derivation is at 202-209. No expert field enters this algorithm. Allocation **capacity** can vary with expert memory use; this is why the run separately checks actual free blocks. Capacity is not asserted equal to native TP8.
- Native traces establish **139 segments, 10 maximum chunks**, not the logical member count 167. A defensible exact CPU segment calculation requires the native allocated tensor views/aliases/strides and backend dimensions. This implementation does not invent that information. The runtime records `_meta` page sizes and logical block strides in int32 units, global kernel block size, segments and max chunks, plus actual cache groups/table block sizes. It rejects a mismatch before any measurement.
- Dummy finalizers are inherited unchanged from `dsv4_attention_runner.patch_dummy_weight_finalizers`: `nvidia/model.py:765-767` finalizes experts only when MegaMoE is selected; 1366-1370 iterates layers and prepares mHC weights; 1542-1543 runs both on weight load. Reduced expert count is accepted by the non-MegaMoE factory and does not alter the mHC finalizer. Existing `frontier/profiling/moe/balanced_routing.py:18-30` accepts `1 <= top_k <= router_logits.shape[-1]`, then routes modulo that count. No hash-layer removal or special routing copy is introduced. Worker startup remains a GPU validation item.

Expected table block sizes are `[256,64,64,4,8]`. With first chunk 6144, ceiling division gives entries `[24,96,96,1536,768]`, total 2520. Both CPU planning and runtime check these values. Block zeroing uses consecutive free IDs `1..n`, excludes null block 0 and checks available capacity. The zeroer has no ID-dependent branch: count, segments and pages fix launched work; IDs only select addresses with the same regular stride. Timing equivalence for arbitrary nonconsecutive address patterns is not claimed. Direct writes stage distinct continuing `(group,row)` pairs of one entry, plus distinct new full rows, through native `append_block_ids` with overwrite false/true. Native baseline row restoration runs outside the measured range.
